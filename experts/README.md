# 学工Buddy 智能体（专家）体系 · 落地手册

> 适用条件：已有产品、想接第三方平台承载智能体、暂无可接入的学生数据与知识库。
> 目标：用**纯提示词**先跑通首批 5 个辅导员专家，验证价值后再接数据和知识库。

---

## 一、结论先行

1. **专家 = 一份配置包，不是新模型。** 不需要训练、不需要微调。
2. **提示词源文件必须存在你自己这边**，平台只负责执行。否则换平台 / 私有化时要重写一遍。
3. **你只需要建两张表**：`expert`（专家注册表）+ `expert_session`（会话与专家绑定关系）。
4. 首批 5 个专家，纯提示词即可上线，**不依赖任何学生数据**——信息由辅导员手动粘贴。

---

## 二、承载方案选型

| 方案 | 上手速度 | UI 可控性 | 数据合规 | 适合场景 |
|---|---|---|---|---|
| **Coze（扣子）建 Bot + Web SDK** | 最快，1–3 天 | 中，样式可部分配置 | 数据在平台侧 | 快速验证、做 Demo 给学校看 |
| **Dify 开源应用（Chatflow）** | 1 周左右 | 高，支持 iframe 嵌入 WebApp | **可私有化部署到学校机房** | 学校要求数据不出校 |
| **自建注册表 + 直连大模型 API** | 2–3 周 | 最高，UI 完全自己画 | 完全自控 | 已有后端，产品 UI 要统一 |

### 决策规则

- 想**最快看到效果** → Coze。把本目录 5 个 md 文件的正文直接粘进 Bot 的人设与回复逻辑。
- 学校明确**要求数据不出校** → Dify 私有化，或直接用学校已采购的模型服务。
- 产品**已有后端、UI 要求统一** → 自建注册表 + 直连 API（推荐，长期成本最低）。

> 建议路径：Coze 验证 → 跑通后把提示词原样迁到 Dify 或自建。
> 因为提示词存在本地 md 里，迁移成本≈0。

## 三、推荐架构（针对"已有产品"）

```
你的产品前端
    ↓  /api/experts      拉取专家列表（名称/分类/头像/示例问题）
    ↓  /api/chat         带 expert_id 发起对话
你的后端（薄适配层）
    ↓  根据 expert_id 取出 system_prompt，拼上历史消息
第三方平台 / 大模型 API
    ↓
你的后端（可选）→ 落库、埋点、敏感词过滤
```

**薄适配层是关键。** 哪怕现在只用 Coze，也别让前端直连 Coze。中间留一层，将来换平台只改这一层。

### 接口建议

```
GET  /api/experts
     → [{ id, name, category, avatar, desc, samples[], sort }]

POST /api/chat
     body: { expert_id, session_id, messages[] }
     → SSE 流式返回
```

`samples` 字段别省。辅导员打开一个空对话框是不知道该问什么的。

## 四、嵌入现有产品的三种方式

| 方式 | 改动量 | 体验 | 说明 |
|---|---|---|---|
| iframe 嵌平台 WebApp | 最小 | 一般，风格割裂 | 一周内上线用这个 |
| 平台 Web SDK | 小 | 较好 | Coze 提供 chat SDK，可传变量、换主题色 |
| **调 API 自绘 UI** | 中 | 最好 | 推荐：气泡、专家卡、示例问题、历史会话全部自己控 |

辅导员产品通常有 PC 端 + 移动端，UI 一致性重要，**建议直接走第三种**。

## 五、专家注册表 Schema

见 `experts/index.json`。核心字段：

| 字段 | 作用 | 必填 |
|---|---|---|
| `id` | 后端与平台 Bot 的映射键 | 是 |
| `name` / `desc` / `category` | 专家广场展示 | 是 |
| `avatar` / `accent` | 卡片视觉 | 是 |
| `samples[]` | 冷启动示例问题，3–4 条 | 是 |
| `trigger_words[]` | 后续做关键词路由用 | 否（二期） |
| `temperature` | 写作类 0.7，研判类 0.3 | 是 |
| `platform_bot_id` | 第三方平台的 Bot ID | 否（接平台时填） |
| `prompt_file` | 提示词源文件路径 | 是 |
| `boundary` | 合规边界，展示给用户在专家详情页 | 是 |

**`prompt_file` 与 `platform_bot_id` 分开存**，就是为了将来自由换平台。

## 六、首批 5 个专家

| id | 名称 | 解决什么 |
|---|---|---|
| `talk-coach` | 谈心谈话教练 | 谈话前给提纲、谈话中给话术、谈话后出规范记录 |
| `psych-crisis` | 心理危机应对顾问 | 信号识别、风险分级、处置流程、转介与家长沟通话术 |
| `official-writing` | 笔杆子 | 通知、公示、新闻稿、讲话稿、述职、计划总结 |
| `funding-award` | 资助与评奖专员 | 资助政策、综测规则、资格初筛、公示与异议处理 |
| `academic-warning` | 学业预警助手 | 学业数据研判、归因分析、帮扶方案、家长沟通函 |

第二批（跑通后补）：就业指导师、突发事件处置官、班团建设助手、宿舍关系调解员、家校沟通顾问、党团发展指导。

## 七、实施排期（4 周）

| 周次 | 任务 | 产出 |
|---|---|---|
| 第 1 周 | 建注册表、专家广场页、显式选择对话；5 个提示词调优 | 产品里能选专家并对话 |
| 第 2 周 | 补示例问题、开场白、专家详情页边界说明；找 3–5 位辅导员内测 | 内测反馈清单 |
| 第 3 周 | 加触发词路由 + 会话归档（记录可导出） | 辅导员开始复用 |
| 第 4 周 | 接知识库：学校公文模板、资助文件、危机干预手册 | 从"通用"变"本校" |

## 八、风险与合规（务必逐条落实）

1. **心理类必须写死边界**：不诊断、不开药、不给学生贴标签；识别到高危信号时，第一输出是"立即陪伴 + 转介"，而不是分析。已在 `psych-crisis.md` 中内置。
2. **学生隐私**：辅导员粘贴的信息可能含姓名学号。产品侧要做输入提醒与脱敏建议；日志落库前脱敏。
3. **政策类必须标注"以本校最新文件为准"**：资助、评奖政策各省各校差异大，模型会编。已在 `funding-award.md` 中内置。
4. **提示词要版本管理**：放进 Git，改动走评审。提示词改坏一个字，线上专家就废了。
5. **专家数量克制**：首批 5 个足够。超过 8 个，用户只会用通用问答。
6. **输出要可导出**：辅导员最终要的是能交的材料（Word / 表格），不是一段聊天文字。二期必须做导出。

## 九、目录说明

```
学工buddy-智能体/
├── README.md                      本文件（操作手册）
├── index.json                     专家注册表，产品后端可直接读
├── talk-coach.md                  谈心谈话教练
├── psych-crisis.md                心理危机应对顾问
├── official-writing.md            笔杆子
├── funding-award.md               资助与评奖专员
└── academic-warning.md            学业预警助手
```

每个 md 文件：**YAML 头 = 产品配置，正文 = 可直接粘贴到平台的 System prompt**。
整个文件夹即一个自包含的交付包，直接拷进项目仓库或整体上传到第三方平台均可。
